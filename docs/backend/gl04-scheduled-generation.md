# GL04-GP01 — التوليد المجدول لمسودات القيود

يتضمن **وضع Scheduled** مقابل Manual وخدمة اختيار المواعيد المستحقة، وترقية SQL رقم 019 التي تعدّل قيد `GenerationMode` دون إعادة كتابة البيانات أو القيود التاريخية.

## واجهة التشغيل

- `POST /api/v1/companies/{companyId}/recurring-journals/run-due` مع JSON `{"asOf":"2026-09-30","limit":100}`.
- تتطلب هوية JWT مفوضة بعضويّة الشركة وصلاحيتَي `RecurringGenerate` و`Draft` في الفروع المسموحة؛ لا توليد بعد اليوم الحالي حسب UTC، ولا أكثر من 100 موعد في الدفعة.
- تعرض النتائج `selectedCount` و`generatedCount` و`failedCount`، مع نتيجة لكل قالب وفترة؛ يعرض `period_closed` موعدًا غير قابل للتوليد. القوالب اليدوية مستبعدة.
- `sched:{templateId}:{fiscalPeriodId}` هو مفتاح إعادة المحاولة، وفهرس SQL يمنع أكثر من قيد للقالب والفترة، حتى بعد إلغاء مسودته أو السباق بين نسختين. التوليد ينتج **Draft** لا يصدر اعتمادًا أو ترحيلًا أو Outbox للأثر المالي.

## خدمة الخلفية المفعلة اختياريًا

**معطلة افتراضيًا** لحماية الشركات من توليد قيد دون اعتماد نشر صريح. يجب تجهيز مستخدم هوية موجودة في عضوية الشركات المسموح لها مع `RecurringGenerate` و`Draft`، وعدم إعطائه صلاحية superadmin.

```text
RecurringScheduler__Enabled=true
RecurringScheduler__ActorSubject=<pre-provisioned-membership-subject>
RecurringScheduler__IntervalMinutes=15
```

عند التفعيل يعمل `RecurringDraftScheduler` عند بدء الخادم ودوريًا كل 15 دقيقة افتراضيًا، ويستخدم UTC للموعد. يكتشف الشركات بواسطة عضوية المشغل، ويخلق نطاق خدمات مستقلًا لكل شركة، وينفذ المعاملة الأصلية للتوليد (تفويض متجدد وتدقيق وترقيم ذري) حتى 100 موعد بكل شركة في كل دورة. لا يولّد أبدًا للفرع الذي لا يملك المشغل صلاحياته، ولا يُعتمد/يُرحّل قيد تلقائيًا. يجب ضبط تشغيل خدمة الـVPS وتوافرها ومراقبتها منفصلًا عن نجاح CI، وهي غير مفعلة إنتاجيًا بإضافة الكود وحدها.

## بوابة الاختبار والمتبقي

`RecurringTests`: الاستحقاق والإعادة والتعطيل والصلاحيات وعدم الترحيل. `RecurringSqlIntegration`: تسعة مواعيد SQL مستقلة. `HostedApiIntegration`: استدعاء HTTPS/JWT وتاريخ الاستخدام. `SchemaUpgradeIntegration`: ترقية 018→019 ذرية وقابلة للإعادة وتراجع آمن عند فشل. تُسجل نتيجة GitHub Actions الحقيقية في PROGRESS بعد اكتمال الاختبار.
