# GL05/GL06 — مراجعة ومعالجة القيود جماعيًا

مرجع التنفيذ: تحليل GL05 وGL06، document-lifecycle وposting-sequence وقواعد BR02/BR05/BR06/BR09/BR18. يظل الأستاذ العام القسم النشط. هذه دفعة داخله، ولا تعني اكتمال القسم أو الشاشتين. لا ترقية قاعدة بيانات؛ المخطط 016.

## قائمة المراجعة والمعاينة

`GET /api/v1/companies/{companyId}/journals/processing-queue` يتطلب periodId، ويقبل branchId وstate وsource وsequenceFrom وsequenceTo وaction وoffset/limit. الإجراء approve افتراضيًا، أو return أو post. الحالة الافتراضية Submitted للاعتماد/الإعادة وApproved للترحيل. نطاق التسلسل رقمي شامل داخل الفترة المحددة، وليس مقارنة نصية لأرقام سنوات متعددة. قائمة المصدر هي JournalSource الموجودة، وليست دليل أنواع قيود GL14.

تتطلب القراءة ledger.read وصلاحية الإجراء الحالية. لا تعرض إلا الفروع المسموحة، وتتحقق من مرجع الفترة والشركة والنطاق. ترجع صفحة عناصر JournalProcessingPreview: ملخص القيد وإصداره ومجاميعه وCanExecute وErrorCode وCheckedAt. المعاينة تعرض مانعًا رئيسيًا لكل قيد ولا تغيره. `GET /journals/{id}/processing-preview?action=approve|return|post&reason=...` لمعاينة قيد محدد؛ الإعادة تحتاج سببًا، ولذلك تعرض قائمة الإعادة invalid_text إلى أن يحدد السبب لكل قيد. لا تحفظ المعاينة حجزًا أو إذنًا دائمًا.

التحقق يشمل حالة الشركة وبياناتها والمصدر وحالة القيد، والفترة والفرع والبطاقات واتزان القيد عند الاعتماد والترحيل، وفصل المنشئ عن المعتمد، وترابط أصل العكس عند ترحيله. لا تمرر قيود المخزون الآلية عبر دورة الأستاذ المنفردة؛ تعالج من مصدرها. يعاد التحقق داخل معاملة التنفيذ، بما فيه الإصدار المتوقع.

## عقد التنفيذ

`POST /api/v1/companies/{companyId}/journals/process-batch`

```json
{
  "action": "post",
  "items": [
    {
      "journalId": "00000000-0000-0000-0000-000000000001",
      "expectedVersion": "00000000-0000-0000-0000-000000000002",
      "idempotencyKey": "unique-document-command-key",
      "reason": null
    }
  ]
}
```

من 1 إلى 100 قيد، ومعرف وإصدار ومفتاح غير فارغ لكل عنصر. الإجراء واحد للدفعة: approve أو return أو post. لا تكرر القيد أو المفتاح داخل الطلب. تتحقق بنية الدفعة كاملة قبل أي تنفيذ. هذا المسار **لا يستخدم رأس Idempotency-Key عامًا**؛ المفتاح داخل كل عنصر هو عقد إعادة الطلب، وOpenAPI يعكس ذلك. لا يشترط أن تملك الدفعة هوية واحدة؛ يمكن إعادة العناصر نفسها بترتيب مختلف أو إرسال العناصر الفاشلة فقط بمفاتيحها.

كل عنصر معاملة مستقلة تحت قفل الشركة. النجاح يحفظ تغيير القيد، والتدقيق المعتاد وسجل journal.processing-succeeded، وOutbox عند الترحيل، وإيصال الطلب معًا. فشل عنصر لا يتراجع عن العناصر التي نجحت. الرد HTTP 200 يعني أن نتائج العناصر متاحة، وليس نجاح الجميع: AllSucceeded وSucceededCount وFailedCount وRows تحدد النتيجة. لا تستخدم SucceededCount وحده لإغلاق الدفعة في العميل.

- رفض التحقق قبل أي تعديل يحفظ journal.processing-rejected مع الإجراء والإصدار المتوقع ورمز الخطأ ومفتاح العنصر وإيصال `Rejected:<code>`، دون تغيير القيد. RejectionRecorded=true. تكرار المفتاح يعيد القرار نفسه حتى إن تغيرت حالة القيد؛ لمحاولة جديدة بعد التصحيح اقرأ الإصدار الحالي وأرسل مفتاحًا جديدًا. تغيير محتوى العنصر بمفتاح سابق يرفض بتعارض idempotency.
- رفض الصلاحية أو الفرع أو المرجع لا يكشف إيصالًا أو بيانات قيد، ولا يدعي حفظ رفض. الصلاحيات يعاد فحصها حتى لإعادة نجاح سابق.
- تعارض تخزين معروف مثل database_constraint يعيد نتيجة فشل للعنصر مع RejectionRecorded=false؛ تتراجع الحركة والتدقيق والإيصال، وتتابع الدفعة العناصر التالية. بعد إزالة السبب يمكن إعادة المفتاح نفسه؛ النجاحات السابقة تعود بإيصالاتها دون مضاعفة الأثر.
- انقطاع اتصال أو إلغاء الطلب أو خطأ تقني غير مصنف يوقف الطلب وقد يكون بعض العناصر السابقة قد التزم. لا تدعي API نجاحًا كليًا أو rollback للدفعة. أعد الطلب بمفاتيح العناصر نفسها لاسترجاع الإيصالات واستكمال العمل بأمان. لا يوجد عامل خلفي يستمر بعد إلغاء الطلب.

## السجل والتزامن

`GET /journals/{id}/processing-history?offset=0&limit=50` يعرض قرارات المعالجة المحفوظة (نجاح/رفض تحقق)، ويتطلب audit.read على جميع الفروع بالإضافة إلى قراءة القيد ضمن النطاق، مثل سياسة التدقيق الحالية. سجل ثابت؛ لا تعديل أو حذف. تفاصيل الأخطاء التقنية التي حالت دون حفظ المعاملة ليست محفوظة فيه ولا تُقدّم كأنها محفوظة.

أضيف تفريغ ChangeTracker داخل SqlTransactionRunner بعد الحصول على قفل الشركة وقبل التفويض لكل أمر. السبب: خدمة scoped يمكنها تشغيل أوامر متعددة، ويجب ألا تعيد استخدام عضوية أو فترة أو إصدار محمل قبل معاملة سابقة. ليس مسموحًا تجهيز تعديلات خارج callback الأمر ثم توقع حفظها؛ جميع تغييرات الأوامر تبقى داخله. يثبت اختبار SQL أن سحب صلاحية الترحيل خارجيًا لا يتجاوز بإعادة إيصال عبر عضوية tracked قديمة.
