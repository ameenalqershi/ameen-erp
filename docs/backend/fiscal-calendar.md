# التقويم المالي SYS03

يدعم إنشاء السنة تقويمًا شهريًا افتراضيًا أو فترات صريحة وفق حقول التحليل. هذه إضافة إلى التقويم الحالي؛ لا تعيد تقسيم سنة قائمة أو تغيّر فترات القيود السابقة. تبقى الشاشة جزئية: تعديل التقويم القائم، والإصدار العددي، والتقويم الخاص بالفرع، وإقفال السنة الشامل لم تنفذ.

## الإنشاء

`POST /api/v1/companies/{companyId}/fiscal-years` يتطلب `company.configure` لكل الفروع و`Idempotency-Key`. يبقى العقد السابق صالحًا: إغفال `periods` أو إرسال null يولد فترات عند نهاية الأشهر الميلادية، مع اختصار أول وآخر شهر وفق حدود السنة. إرسال قائمة فارغة مرفوض.

مثال فترتين مخصصتين:

```json
{
  "code": "2027",
  "startsOn": "2027-01-01",
  "endsOn": "2027-12-31",
  "periods": [
    {"code":"2027-H1","startsOn":"2027-01-01","endsOn":"2027-06-30"},
    {"code":"2027-H2","startsOn":"2027-07-01","endsOn":"2027-12-31"}
  ]
}
```

السنة من يوم إلى 367 يومًا وفق القيد الحالي، والفترات من 1 إلى 367، كل منها يوم على الأقل. ترتب الفترات بالتاريخ ثم يتحقق من تغطية حدود السنة بالضبط دون فجوة أو تداخل. رموز الفترات فريدة على مستوى الشركة، لا السنة فقط. الحالات والهوية ومعرف السنة تولد من الخادم؛ لا يقبل الطلب فترة مقفلة أو ربطًا بمعرف سنة آخر. يمكن استعمال تقويم 4-4-5 بإرسال تواريخه الفعلية؛ لا توجد سياسة توليد تلقائي لهذا النمط.

لا تتداخل السنوات ولا تتكرر رموزها. بداية أول سنة تطابق بطاقة الشركة، ولا تقبل سنة تسبق البداية المحددة في البطاقة بعد ذلك. لا يشترط التنفيذ اتصال السنوات المختلفة؛ شرط عدم الفجوات يخص الفترات داخل السنة. الحفظ ذري للسنة وفتراتها والتدقيق والإيصال، ومعاملة الشركة تمنع تزامن إنشاء سنوات متداخلة. إعادة المفتاح والمحتوى نفسيهما تعيد الإيصال نفسه بعد التحقق من الصلاحية.

## القراءة والاستخدام

جميع المسارات التالية تحت `/api/v1/companies/{companyId}/fiscal-years`:

| المسار | النتيجة والصلاحية |
|---|---|
| GET /search?search=2027&offset=0&limit=50 | بحث برمز السنة وترتيب تنازلي حسب بدايتها؛ ledger.read |
| GET /{id} | السنة وفتراتها مرتبة وحالة إقفال الأستاذ المشتقة؛ ledger.read |
| GET /{id}/usage | أعداد القيود كلها وغير المرحلة والتوليدات الدورية؛ ledger.read لكل الفروع |
| GET /{id}/audit-events | إنشاء السنة وإقفال وفتح فتراتها، مع الصفحات؛ read + audit.read لكل الفروع |

التقويم مشترك للشركة، فتتاح بياناته للقراء المصرح لهم حتى إن كانت عضويتهم محدودة بفرع. ملخص الاستخدام والتدقيق يتطلبان النطاق العام حتى لا يكشفا نشاط الفروع الأخرى. `journalCount` يشمل الملغى، و`unpostedJournalCount` يحسب Draft وSubmitted وApproved فقط. سجل السنة الجديد يحفظ معرفات الفترات ورموزها وحدودها؛ سجلات الإنشاء القديمة لا تكتسب هذه التفاصيل بأثر رجعي.

حالة التقويم `Open` عندما لا توجد فترة مقفلة، و`PartiallyClosed` عند إقفال بعضها، و`Closed` عند إقفال جميعها. جميع النتائج تحمل `generalLedgerOnly=true`: هذه الحالة وصف لإقفال فترات الأستاذ، وليست اعتمادًا لإقفال بقية وحدات ERP أو ترحيل أرباح السنة. لا توجد عملية تعطيل سنة أو فتح ضمني عبر تعديل البطاقة؛ يظل الإقفال والفتح عبر GL11/GL12 بصلاحياتهما وسببهما وإصدارهما.

القيد يختار الفترة حسب تاريخ الأثر، وتبقى فحوص الإقفال والاتزان وفصل المهام كما هي. GL04 يسمح بتوليد واحد للقالب لكل فترة؛ إن احتوت الفترة أكثر من موعد للقالب، يرفض التقويم الدوري والتوليد برمز `ambiguous_recurring_period`. لا يختار موعدًا واحدًا ويسقط الباقي. يلزم تقسيم مناسب عند إنشاء السنة أو استخدام قيد يدوي وفق الصلاحيات؛ إعادة تصميم التوليد المتعدد ليست ضمن هذه الدفعة.

لا تتطلب الإضافة ترقية SQL جديدة؛ إصدار المخطط يبقى 7، وتستخدم الجداول القائمة. لا تطبق أي تعديل على السنوات القديمة. بيانات الحالة والعدد في الاستعلامات ليست لقطة معاملات مضمونة أثناء الكتابة المتزامنة، ولم يثبت الأداء على أحجام إنتاج كبيرة.

اختبارات [FiscalCalendarTests.cs](../../backend/tests/Ameen.Erp.Tests/FiscalCalendarTests.cs) و[FiscalCalendarSqlIntegration.cs](../../backend/tests/Ameen.Erp.Tests/FiscalCalendarSqlIntegration.cs) تتحقق من التغطية والترحيل والصلاحيات والإعادة والتراجع والتزامن ودور التشغيل. يختبر المضيف الفعلي المسارات عبر HTTPS وJWT.
